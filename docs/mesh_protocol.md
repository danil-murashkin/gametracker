# LoRa mesh: мастер ↔ устройства

Протокол взаимодействия игрового сервера (мастер) с трекерами и станциями в **mesh-сети LoRa**. Runtime трекера после успешного разбора кадра вызывает показ текста и/или `applyRecipe` — см. [`device_runtime.md`](device_runtime.md). Физический слой (частота, SX126x/LLCC68 и т.п.) — вне этого документа; здесь логика кадров, адресации и шифрования.

---

## 1. Участники

| Узел | Роль |
| ---- | ---- |
| **Мастер** | Игровой сервер + UI организатора; источник групповых и персональных команд; приёмник телеметрии |
| **Станция связи** | Шлюз LoRa ↔ сервер; обычно всегда на приёме у штаба |
| **Трекер** | Устройство игрока; GNSS uplink; приём downlink; может ретранслировать чужие кадры |
| **Ретранслятор** | Выделенный узел или режим трекера/станции: store-and-forward без доступа к plaintext |

Топология — mesh: кадр доходит до адресата через один или несколько hop. Промежуточный узел **не расшифровывает** полезную нагрузку.

```text
  Мастер ──► Станция ──► (релей) ──► Трекер A
                 │                      │
                 └──────── (релей) ─────┴──► Трекер B
```

---

## 2. Идентификаторы

| ID | Назначение |
| -- | ---------- |
| `device_id` | Уникальный id трекера (или станции в роли узла) |
| `master_id` | Id мастера / игровой сессии |
| `group_id` | Группа рассылки (команда, фракция, «все игроки», …) |
| `msg_id` | Id сообщения для дедупа и ACK |
| `hop_ttl` | Оставшееся число ретрансляций |

Ключи выдаются при **регистрации / настройке** трекера (Wi‑Fi или BLE provisioning), не открытым текстом в эфире mesh.

---

## 3. Адресация

| Режим | Кто читает plaintext | Когда |
| ----- | -------------------- | ----- |
| **unicast** | мастер и один `device_id` | телеметрия трекера → мастер; персональная команда мастер → трекер |
| **group** | мастер и все устройства с данным `group_id` | объявления, массовые эффекты, смена фазы сценария |
| **mesh-control** | по необходимости только заголовок | маршрут, ACK, probe — без игрового payload или с минимальным служебным |

Широковещание «всем подряд без ключа» для игровых данных **не** используется: даже group-кадры закрыты ключом группы.

---

## 4. Логический формат кадра

```text
[ route_header | addr_type | dst | src | msg_id | hop_ttl | nonce | ciphertext | tag ]
```

| Поле | Видно релею | Содержание |
| ---- | ----------- | ---------- |
| `route_header` | да | версия, флаги, длина |
| `addr_type` | да | `unicast` \| `group` \| `mesh_ctrl` |
| `dst` / `src` | да | `device_id` / `group_id` / `master_id` |
| `msg_id` | да | дедуп |
| `hop_ttl` | да | уменьшить на 1 при forward; 0 → не слать дальше |
| `nonce` | да | уникален в контексте ключа (счётчик / random) |
| `ciphertext` | да, но непрозрачен | AEAD-шифртекст полезной нагрузки |
| `tag` | да | аутентификация AEAD |

Релей принимает решение о forward по заголовку и таблице соседей / недавних `msg_id`. Расшифровка — только у узлов с подходящим ключом.

---

## 5. Типы полезной нагрузки (после расшифровки)

### Трекер → мастер (unicast)

| Тип | Поля (минимум) | Когда |
| --- | -------------- | ----- |
| `telemetry_gnss` | lat, lon, alt?, fix_age, `device_id`, tick? | период или по событию |
| `telemetry_status` | `is_dead`, battery?, last_error? | вместе с GNSS или отдельно |

### Мастер → трекер (unicast)

| Тип | Действие на трекере |
| --- | ------------------- |
| `cmd_text` | показать текст на экране |
| `cmd_apply` | `applyRecipe(name)` (квест, удар, бафф с сервера) |
| `cmd_reset` | сброс состояния персонажа к исходной модели / слоту (после смерти у мастера) |
| `cmd_set_group` | вступить / выйти из `group_id` (ключи группы — отдельным secure provisioning) |

### Мастер → группа (`group`)

Те же `cmd_text` / `cmd_apply` / служебные, но `dst = group_id`. Каждый член группы расшифровывает своим **групповым** ключом и исполняет локально.

Пример сценария: шаг 12 Fallout Demo — мастер шлёт **unicast** `cmd_apply` с рецептом инсульта на один `device_id`.

---

## 6. Шифрование и целостность

Требование: **даже в mesh** пакет игровых данных понимают только мастер и адресат (устройство или члены группы).

| Канал | Ключ | Кто держит |
| ----- | ---- | ---------- |
| Unicast мастер ↔ устройство | `K_device` (парный) | мастер + этот трекер |
| Group | `K_group` | мастер + члены группы |
| Mesh-control (опционально) | сетевой ключ сессии | все узлы mesh **или** только станции — не для статов/квестов |

- Алгоритм на уровне спеки: **AEAD** (например ChaCha20-Poly1305 или AES-GCM): `ciphertext + tag` из plaintext payload и AAD = стабильная часть заголовка (`addr_type`, `dst`, `src`, `msg_id`).
- **Антиповтор:** монотонный счётчик/nonce на ключ; получатель отбрасывает повтор и слишком старый nonce.
- Релей **не** имеет `K_device` / `K_group` игровых каналов → не читает координаты, команды и тексты.
- Подделка команды без ключа отсекается проверкой `tag`.

Ротация: при компрометации или смене сессии игры — переиздание ключей через provisioning (вне mesh plaintext).

## 7. Ретрансляция и дубликаты

1. Узел принял кадр с валидным заголовком и `hop_ttl > 0`.
2. Если `msg_id` уже видели недавно — отбросить.
3. Если `dst` — мы (unicast на наш `device_id` или group, в которой мы) — попытка AEAD; успех → очередь runtime; при необходимости ACK unicast мастеру.
4. Если мы не адресат (или group — всё равно можно ретранслировать по политике) — уменьшить `hop_ttl`, поставить в очередь TX соседям.
5. Не менять `ciphertext` / `tag`.

Ограничение флуда: rate-limit на forward с одного `src`, потолок размера очереди.

---

## 8. Связь с runtime трекера

После успешного AEAD:

1. Разобрать тип payload.
2. `cmd_text` → UI-очередь сообщений.
3. `cmd_apply` → `applyRecipe` по правилам [`device_runtime.md`](device_runtime.md) (в т.ч. «ПУСТО», если уже мёртв — по политике сценария; квест инсульта обычно применяется, пока ещё жив).
4. `cmd_reset` → очистить эффекты/инвентарь по слоту, снять `is_dead`, перезагрузить world `pasv`.
5. Uplink GNSS не прерывает тик 1 Гц: готовится в фоне, уходит при окне TX.

Симуляция без радио: мастерский downlink = прямой `applyRecipe` в engine — [`scenario_simulation.md`](scenario_simulation.md).

## 9. Примеры

**Трекер шлёт координаты**

1. Трекер собирает `telemetry_gnss`, шифрует `K_device`, `dst = master_id`, `addr_type = unicast`.
2. Кадр идёт через соседей на станцию.
3. Мастер расшифровывает, обновляет карту.

**Мастер: инсульт одному игроку**

1. Мастер: `cmd_apply` / имя рецепта смерти, `dst = device_id`, AEAD на `K_device`.
2. Трекер расшифровывает → apply → HP 0, сообщение на экран, freeze тика.
3. Игрок идёт к мастеру; мастер шлёт `cmd_reset` или сбрасывает офлайн.

**Мастер: объявление группе**

1. `cmd_text` «Фаза 2 началась», `dst = group_id`, ключ `K_group`.
2. Все члены группы показывают текст; узлы вне группы кадр не читают (нет ключа), могут лишь ретранслировать заголовок.

---

## 10. Вне скоупа этого документа

- Конкретные частоты LoRa, SF, мощность, антенны.
- IP/API сервера мастера (REST/WebSocket) — лишь то, что станция отправляет/принимает те же логические payload.
- Реализация в `firmware/` — последующий этап после стабилизации спеки.
